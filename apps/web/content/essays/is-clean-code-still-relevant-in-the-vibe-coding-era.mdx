When Steve Jobs was building the first Macintosh, he argued with his engineers about the layout of the circuit board inside the case. He wanted the chips laid out neatly. The engineers pointed out that nobody would ever open the case and look at&nbsp;it.

Jobs had learned the opposite from his father, Paul, who built cabinets and fences in the family garage. He explained it to his biographer, Walter Isaacson:

<PullQuote
  quote="When you're a carpenter making a beautiful chest of drawers, you're not going to use a piece of plywood on the back, even though it faces the wall and nobody will ever see it. You know it's there, so you're going to use a beautiful piece of wood on the back. For you to sleep well at night, the aesthetic, the quality, has to be carried all the way through."
  attribution="Steve Jobs, in Walter Isaacson's biography"
/>

I have been having a version of that argument about&nbsp;code.

## Code as the inside of the case

With vibe coding, you describe what you want, a model writes it, you run it, and if it works you move on. The user sees the app and never the source, so the code starts to look like that circuit board. The obvious question is why the inside should be tidy if the app&nbsp;works.

I think clean code matters more now than it did before, for three practical&nbsp;reasons.

## The model reads the code before it writes

A compiler does not care whether a function is called `handleUserAuthentication` or `x7`. A language model does. It works from the context it is given, and the existing code is most of that context. Clear names, small functions with one job, one convention per task and comments that explain why all make the next suggestion more likely to be&nbsp;right.

Messy code makes the model guess. A function that quietly does five things, or three conventions for the same database call, leaves it to pick one. That is where most of the subtle bugs I find in generated code come&nbsp;from.

## Agents copy the patterns they find

An agent extends a project by following how things are already done in it. If the codebase has one clear way to do something, new code follows that way and the project stays consistent as it&nbsp;grows.

If there are three ways to make a database call and two of them are wrong, the agent copies whichever one it finds. It does not judge whether a pattern is good, so every new feature can add more of the inconsistency that was already&nbsp;there.

## A person still has to fix it

At some point someone has to change the code by hand. The model gets stuck on a bug, a decision from three weeks ago turns out to be wrong, or something breaks in production. With AI in the loop this happens less often, but when it does, the person fixing it is reading code they did not write, under time&nbsp;pressure.

Readable names, small functions and clear boundaries are what make that fix quick. In a messy codebase, a change that should take five minutes can take an&nbsp;afternoon.

## Generated code gets the same standard

I hold generated code to the same standard as code written by hand: good names, small functions, one pattern per job, and a bad pattern fixed before an agent copies it. The code now has more readers than it used to. There is me, the people I work with, the model that writes it and the agents that maintain&nbsp;it.
