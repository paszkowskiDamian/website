## TL;DR

- Each project has a Notion workspace with three databases: Ideas, Epics and Tasks. Notion holds the plan and the status, and the repo holds the code.
- A workflow runs Claude agents in fixed roles: product review, architecture, design, development and review. Each role reads its items from Notion, does its part and moves them on.
- On Depth Map Studio, one epic of 14 tasks shipped as a single pull request with 39 end-to-end tests named after the task IDs.

This website started on a Trello board: I wrote cards, and Claude picked them up and opened pull requests. For bigger projects I moved the tasks into Notion and wrote the process down as a workflow that runs Claude agents in fixed&nbsp;roles.

## The Notion side

Every project starts from the same template page, with three databases:

- **Ideas**: raw ideas, which end up Converted or Rejected.
- **Epics**: larger bodies of work, each with a goal and success criteria.
- **Tasks**: units of work with acceptance criteria, a track (Frontend, Backend, Full-Stack or N/A), and Depends On and Blocks links to other tasks.

Epics and tasks also carry four checkboxes: Research Ready, Spec Ready, Architecture Ready and Design Ready. A task moves from To Do to In Progress, In Review and Done, and can be Cancelled at any&nbsp;point.

## The roles

The workflow starts with a discovery agent that reads the board and sorts every item by what it needs next. Then it runs one agent per item, in parallel:

1. **Product reviewer** turns a new idea into an epic or tasks and writes the research and specification, or rejects the idea.
2. **Architect** decides the technical approach once per epic, so all of its tasks build on the same decision.
3. **Designer** produces mockups for Frontend and Full-Stack work. Backend tasks skip this step and can start as soon as the architecture is ready.
4. **Developer** implements one task in its own git worktree, then moves it to In Review with notes on what changed and how it was checked.
5. **Reviewer** checks the change against the specification and the acceptance criteria, and either marks the task Done or sends it back with notes.

No role picks up a task while one of its dependencies is unfinished. When a dependency is cancelled, the blocked task waits until the product reviewer confirms it still makes sense. That rule lives in the workflow script, because it was too fragile to build as a Notion&nbsp;formula.

## Depth Map Studio

I seeded the Depth Map Studio board from the repo's backlog: 57 tasks from its task list, plus open items and ideas. It now holds 88 tasks, 44 of them Done, and 20 that depend on other&nbsp;tasks.

The vessel flow redesign epic had 14 tasks, T75 to T88, covering the new workbench layout, seams set by the handle, a casting assistant and the master step. Claude read the epic and its task pages from Notion and split the work between parallel agents, one per task or pair of closely related tasks, with extra agents for the interface passes and the test&nbsp;suite.

It shipped as one pull request with 73 commits across 91 files. The end-to-end suite has 39 tests, each named after the task it checks, for example "T79 · default mug proposes 2 body parts + base". That makes it easy to see which task a failing test belongs&nbsp;to.

## My part

I write the ideas, approve the designs when an epic asks for my approval, and review the pull request and its preview. When a review turns up something that should not happen again, I add it to the agent instructions or the repo's guidelines, so the next task starts with the&nbsp;correction.
