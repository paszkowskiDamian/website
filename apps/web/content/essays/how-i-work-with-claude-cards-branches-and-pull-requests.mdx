## TL;DR

- Tasks for this website live on a Trello board. I write the cards, and Claude picks one, builds it on its own branch and opens a pull request.
- The steps are written down as a skill file in the repo, so every session follows the same process.
- Each pull request says what changed, what was left out and how it was checked. I review the change on a preview copy of the site.
- When I correct something that could happen again, the correction goes into the skill file.

In one day in July, around a dozen pull requests for this website were opened, reviewed and merged: an essays index with filters, project pages, generated cover art, a photo lightbox, an RSS feed and a contact form. I wrote almost none of that code. I had written the Trello cards the night&nbsp;before.

## The board

The board has five lists: DRAFT, TODO, INPROGRESS, INREVIEW and DONE. Only cards in TODO are ready to be picked up. Each card describes what to build and what to leave alone, and at the bottom it lists which cards it depends on and which it&nbsp;blocks.

Writing those cards is most of my work on a task. I spent years in agile teams before this, and the board keeps what worked there: small tickets, a board that shows what is really happening, and dependencies written down before the work&nbsp;starts.

## From card to pull request

When I ask Claude to take the next task, it follows the `work-on-board-task` skill:

1. Look only at TODO, and skip any card whose blocker is not in DONE or that needs access Claude does not have, such as a hosting dashboard.
2. Take the first card that is ready and move it to INPROGRESS before writing any code.
3. Work on a fresh branch, build only what the card asks for, and run the build, type checks and linter before pushing.
4. Open a pull request, move the card to INREVIEW and add a short report to the card.

Several sessions often run at once, each on its own card and branch. Because the cards say who owns what, their changes rarely&nbsp;collide.

Every pull request has three sections: what changed, what was deliberately left out and why, and how it was checked. A typical "left out" note says the header was not touched because card #15 owns the&nbsp;navigation.

## Until it merges

Claude keeps watching the pull request after opening it. A review comment gets a fix or a reply. A failing check gets fixed. A merge conflict gets resolved against the latest `main`. When the pull request merges, the card moves to DONE. If it is closed without merging, the card goes back to TODO with a&nbsp;note.

## Writing better cards

I learned to write these cards by writing a bad one first. My first card for the generated project covers said, more or less, "make the project miniatures feel more like the brand". The result matched the card and was not what I wanted, because the card never said what I&nbsp;wanted.

The second version took an hour. It described the shapes (half circles, quarter circles and petals on a grid, so they join across tiles), a limit on how much red a cover can use, and that each cover is generated from the project's title so it stays the same between builds. That one&nbsp;merged.

## Reviewing the preview

Every branch deploys to its own preview copy of the site, and the link appears on the pull request. I review the change there, the way readers will see it, and read the code as&nbsp;well.

On one new page, the first paragraph ended with a single word on its own line. I left a comment with a screenshot. A few minutes later the fix was in: the last two words are joined with a non-breaking space, so the lone word cannot come back at any screen&nbsp;width.

## Corrections go into the skills

The repo has two skill files. `work-on-board-task` is the process above. `implement-essay` covers essays, from a Notion draft to a published page. The lone-word rule went into `implement-essay` after that comment, and every essay published since follows&nbsp;it.

The board may move from Trello to Notion, where my notes and drafts already are. The skill files describe cards, branches and pull requests, so only the part that finds the board would&nbsp;change.
