## TL;DR

- My projects keep their ideas, epics and tasks in Notion. The repo holds the code.
- A workflow sends Claude agents through five roles: product review, architecture, design, development and review. Each agent reads its items from Notion, does its part and hands them on.
- On Depth Map Studio, a 14-task epic came back as one pull request with 39 end-to-end tests, each named after its task.

The vessel flow redesign for Depth Map Studio started as 14 tasks in Notion and came back as one pull request: 73 commits, 91 files and 39 end-to-end tests, each named after the task it&nbsp;checks.

This website started on a Trello board. I wrote cards, and Claude picked them up and opened pull requests. For bigger projects I moved the tasks into Notion and wrote the whole process down as a workflow that runs Claude agents in fixed roles. Here is how it&nbsp;works.

## Everything starts in Notion

Every project gets the same template page with three databases:

- **Ideas** for anything worth considering. Each idea ends up turned into work or rejected.
- **Epics** for bigger pieces of work, each with a goal and success criteria.
- **Tasks** for single units of work, with acceptance criteria, a track (Frontend, Backend, Full-Stack or N/A), and links to the tasks they depend on and block.

Four checkboxes decide when an epic or a task is ready for its next step: Research Ready, Spec Ready, Architecture Ready and Design Ready. Tasks move from To Do to In Progress, In Review and&nbsp;Done.

## Five roles, all at once

First, a discovery agent reads the whole board and sorts every item by what it needs next. Then the workflow starts one agent per item, in parallel:

1. **Product reviewer** takes a new idea and turns it into an epic or tasks, complete with research and a specification. Or it rejects the idea.
2. **Architect** picks the technical approach once per epic, so every task in that epic builds on the same decision.
3. **Designer** makes mockups for Frontend and Full-Stack work. Backend tasks go straight to development as soon as the architecture is ready.
4. **Developer** builds one task in its own git worktree, then moves it to In Review with notes on what changed and how it was checked.
5. **Reviewer** checks the result against the specification and the acceptance criteria, then marks the task Done or sends it back with notes.

Dependencies are strict. No role touches a task while something it depends on is still open. When a dependency gets cancelled, the blocked task waits until the product reviewer confirms it still makes sense. Notion formulas could not express that rule reliably, so it lives in the workflow&nbsp;script.

## What it looked like on Depth Map Studio

I seeded the board from the repo's backlog: 57 tasks from its task list, plus open items and ideas. It has grown to 88 tasks. Of those, 44 are Done and 20 depend on other&nbsp;tasks.

The vessel flow redesign epic covered 14 tasks, T75 to T88: a new workbench layout, seams set by the handle, a casting assistant, and a master step that opens on the printed parts. Claude pulled the epic and all 14 task pages from Notion, then split the work across parallel agents, one per task or pair of closely related tasks. More agents took the interface passes and the test&nbsp;suite.

All of it landed in one pull request. Each of its 39 end-to-end tests carries the ID of the task it checks, for example "T79 · default mug proposes 2 body parts + base", so when a test fails I can see straight away which task it belongs&nbsp;to.

## Where I come in

I write the ideas and approve the designs when an epic asks for my sign-off. I review every pull request and click through its preview. When a review turns up a mistake that could happen again, I add a line to the agent instructions or the repo's guidelines, so the next run starts with that&nbsp;fix.
