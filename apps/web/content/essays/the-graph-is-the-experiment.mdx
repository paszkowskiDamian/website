Making a relief out of a picture is not one model. That was the thing I kept failing to&nbsp;internalise.

You segment the subject from its background. You upscale, because depth models see less than you think. You run a depth estimator, and then usually a second one, because the first is good at broad form and bad at fine detail and the second is the reverse. You fuse them. You level the ground the ornament sits on. You mask. You normalise. You lift the silhouette off the plate. You limit the draft so the thing will actually come out of plaster. The deepest chain I have runs nineteen of these in a row.

And every real question I had was of the form: *what if this step came before that one?*

## The twentieth rewrite

For a while I answered those questions by editing Python. Copy the script, move two function calls, run it, look at the result, lose track of which variant produced which image, do it again.

This is a bad way to live, but the specific badness is worth naming, because it isn't "too much typing." It's that **the thing I was varying had no representation**. The experiment was the ordering — and the ordering existed only as the incidental sequence of lines in a file I kept overwriting. I could not diff two experiments. I could not name one. I could not hand one to someone and say *run exactly this*.

<PullQuote quote="The variable I cared about was the one thing the system had no way to hold." />

So I stopped editing code and made the pipeline a piece of data.

## What that actually means

There is now a registry of node types — fifty-five of them, across ten categories: image, depth, normal, mask, segmentation, edge, text, value, input, output. Each declares what it consumes, what it emits, and what knobs it has.

A pipeline is a JSON file naming some nodes and the wires between them. There are forty of those. A FastAPI service reads one, topologically sorts it, and runs it. And there's a canvas — React Flow — where the graph is a graph: drag a node in, wire it up, run it, see what each stage emitted.

The payoff was immediate and slightly embarrassing in retrospect. Comparisons became cheap enough that *changing one variable at a time* became the default rather than a discipline I had to summon. Six cloud pipelines that differ by exactly one node are six files, and the diff between any two of them is the experiment, written down.

## Two things it did not fix

I want to be careful not to sell this as pure win, because a graph editor makes two promises it can't keep.

**Data has no type checker.** The Studio submits jobs to pipelines by hardcoded ID. Rename a JSON file and the Generate action breaks — at runtime, in the browser, with no compile error and nothing in the editor to warn you. I traded a class of tedium for a class of silent breakage, and the honest summary is that I'd make the trade again but I should have seen the invoice coming.

**The canvas implies parallelism that doesn't exist.** A DAG *looks* like it fans out. This one doesn't: model weights are gigabytes, so jobs run one at a time, and raising the worker count just loads competing copies of the same model until the machine gives up. The visual language of the tool is making a promise about the runtime that the runtime declines. That's a real cost of borrowing a familiar metaphor.

<PullQuote quote="A DAG on a canvas promises you concurrency. Mine runs strictly one node at a time, and nothing on screen says so." />

## The bug that justified the whole thing

The draft limiter — the node that clamps slope so a relief will release from plaster — has to run *after* the final normalise. That last step stretches its input back across the full height range, which scales every slope up by exactly the factor the limiter just removed. Put the limiter earlier and the pipeline runs, reports success, and emits a relief that locks the mould as badly as before.

That bug is invisible in code. It's a function call in the wrong place among nineteen, and every individual line is correct.

On a canvas it's a node in the wrong place in a chain you're looking at. I found it because the graph was in front of me and the ordering was the thing my eyes were on — which is, in the end, the entire argument. When your work is combinatorial, code is a lossy medium for it: it can express any single arrangement and gives you no purchase on the space of arrangements.

Make the arrangement the artifact. Then you can name it, diff it, and see it be wrong.
